# Перенос счёта на сервер: команды по одной (Ж-131, Ж-133)

Статус: разработка, до аудита. Данные — только ≤ 2021-12-31. Адрес и ключ сервера — ваши: `user@host` подставляете сами, в git и логи они не попадают. Код на сервере не правится: он приезжает только tar с хэшем.

## Что зависит от других слияний
- Шаги 1–4 и `./zapusk_sobol.sh train4` на кубе progon работают уже на базе с #609 (проверено локально).
- Куб v5, период `v2`, проходы s1 / s2 / k3 в `zapusk_sobol.sh` включаются только когда в коде есть `fastbt.progon_server` с аргументами `--kub v5 --period --seed --k3 [--n1]` (ветка `progon-server-v5`; скрипт сам смотрит `--help` на `--k3`). До этого `./zapusk_sobol.sh v2` отвечает FAIL с причиной.
- Куб v5 считает оценщик Л9 (`fastbt/eval_v5.py`); до слияния Л9 драйвер откажет «Л9 не слит».
- Коммит для сборки — база после слияния #610, #611 и `progon-server-v5`. Сборку делает дирижёр командой шага 1 на этом коммите.
- v6 (yaml кубов) в пакет войдёт, когда лежит в `fastbt/designs/v6/`: сборщик копирует его сам.

## Шаг 1. На Маке: собрать `perenos/` (одна команда)
```
scripts/server/sobrat_perenos.sh <коммит>
```
Каталог — `perenos/` в корне (нужен пустой; другой — `PERENOS_OUT=...`). Считает эталон Мака (якорь A_fix × 6 Sk и 200 точек), ~1,5 мин на 3 процессах. Ожидается: `OK manifest: 201 файлов, 1.136 ГБ, max_data 2021-12-31, ...`, затем `etalony: ... записей 206, со status = oshibka 0`, последняя строка `OK perenos: ...; kod <12 знаков> (tar sha256 <64>); данных 201 файлов, 1,1G`. Хэш tar (`VERSIYA`) — в журнал. Если в манифесте файл с датой > 2021-12-31 или путь `test_locked` — `FAIL manifest: ...`, каталог не собирается.
Усечённые копии (`data/server_2021/`) берутся из основной копии; если их там нет — `python3 scripts/server/usech_2021.py --koren . --vyhod <куда>/data/server_2021` и `PERENOS_DANNYE_DOP=<корень копий>`.

## Шаг 2. На Маке: отправить на сервер

```
cd perenos && rsync -av --files-from=spisok_perenosa.txt ./ user@host:perenos/
```
Ожидается: список файлов, `sent ... received ...` без ошибок (≈ 1,1 ГБ).

## Шаг 3. На сервере
```
cd perenos && ./razvernut.sh
```
Нужен `python3.9` (иначе `PERENOS_PYTHON=/путь/python3.9`). Ожидается последняя строка: `OK razvernut: python 3.9.x (x86_64), numba 0.60.0, llvmlite 0.43.0, numpy 2.0.2, pandas 2.3.3, pyarrow 21.0.0, scipy 1.13.1; kod <12 знаков> (tar sha256 ...)`. Любой FAIL (нет колеса, sha не сходится) — стоп, вывод дирижёру, версии не менять.

## Шаг 4. Проверка якоря
```
./proverka_yakor.sh
```
Сравнение в два уровня (разбор: `docs/otchety/2026-10-29_kross_arh_ekviv.md`). Дискретное — строго: хэши данных, куба и дат по Sk, `kod`, `vhody`, ключи и статусы строк ledger, сделки по дням, индексы входа/выхода. Непрерывное — Шарп, доходности, ряды: якорь ≤ 1e-12 (Ж-131), точки — допуск из переменной `DOPUSK` (по умолчанию 0, побайтно; меняет только владелец: `DOPUSK=1e-12 ./proverka_yakor.sh`).
Ожидается две строки: `proverka[режим 1]: max |Δ| непрерывных: якорь ... , точки ...; дискретных расхождений 0, непрерывных вне допуска 0` (max |Δ| печатается всегда, и при OK) и `OK [режим 1]: дискретное совпало; ...; отметка .../proverka/OK`. Параметры numba (`NUMBA_NUM_THREADS=1`, `NUMBA_THREADING_LAYER=workqueue`) скрипт печатает и ставит сам, они те же, что при эталоне на Маке.
Режим numpy: `./proverka_yakor.sh --rezhim2` прогоняет оба режима (1 — numpy как есть, 2 — без AVX512-группы и SVML, `NPY_DISABLE_CPU_FEATURES` + `NPY_DISABLE_SVML=1`) и печатает оба итога; режим выбирает владелец и дальше задаёт `PERENOS_REZHIM=<1|2>` при `./zapusk_sobol.sh` (нужна отметка `proverka/OK` либо `proverka/OK_r2` того же режима). Если numpy на сервере ругается на имя в списке AVX512 — список меняется переменной `PERENOS_REZHIM2_FEATURES` (имена из `numpy.show_runtime()`).

**Что делать при FAIL.**
- `FAIL дискретное` (код 1): стоп. Счёт не запускать, ничего не менять, вывод и `proverka/verdikt_*.json` — дирижёру. Это перевернувшаяся сделка, другой ключ ledger (`vhody`) или другие данные; допуском не лечится.
- `FAIL непрерывное` (код 3): дискретное совпало, но Шарп/доходности вне допуска. Счёт не запускать; прислать дирижёру строку FAIL и max |Δ| (якорь и точки). Расширить `DOPUSK` или принять режим 2 решает владелец.
- `OK` при max |Δ| > 0 (допуск владельца): значения в допуске; max |Δ| записать в журнал.
Локально, на том же arm64, Δ = 0.0; на x86 расхождение возможно — это и проверяется.

## Шаг 5. Запуск счёта (в фоне)
```
./zapusk_sobol.sh train4
./zapusk_sobol.sh v2
./zapusk_sobol.sh status train4
```
Ожидается: `OK zapusk train4: pid N, лог logs/sobol_train4_<время>.log`; процессов — ядра − 4. Ledger — `ledger/<период>_<s1|s2|k3>/<Sk>/` (куб v5) или `ledger/train4/<Sk>/` (куб progon); чекпоинт каждые 5 000 точек; `status` печатает по каждой стратегии `закрыто N из M` или `N=… чекпоинт i=…`. Возобновление — повторный запуск той же командой. Остановить — `kill <pid>` из `status`. Без отметки шага 4 или при другом коде/данных — `FAIL`, счёт не стартует.
Малый прогон (проверка): `PERENOS_STRATEGII=S1 PERENOS_TOCHEK=50 ./zapusk_sobol.sh train4` (только замена progon_sobol).

## Шаг 6. Забрать результаты (на Маке)
```
cd perenos && ./zabrat.sh user@host:perenos data/server_rezultaty/<ДД-ММ>
```
Забирает только `ledger/`, `tables/`, `logs/`; ожидается `OK zabrat: N файлов в ... (ledger/, tables/, logs/)`. Если в забранном код или данные — `FAIL`.

## Пины и кэши
`requirements_server.txt` (и `env/requirements_r2.txt`) содержат `numba==0.60.0`, `llvmlite==0.43.0` и пины numpy 2.0.2, pandas 2.3.3, pyarrow 21.0.0, scipy 1.13.1 — версии Мака; сборщик сверяет их с этим Маком (`versii.py`, расхождение — FAIL), `razvernut.sh` — с сервером (строка `OK versii: ...`, расхождение — FAIL). В tar нет `__pycache__` и numba-кэша (сборщик и `razvernut.sh` проверяют); кэши numba — в `cache/numba/`.

## Проверено локально (Мак arm64, каталог в scratchpad)
Сборка → развёртывание → якорь (`OK ... max |Δ| = 0.0e+00; 200 точек побайтно`) → `zapusk_sobol.sh train4` (S1, 50 точек: `чекпоинт 1`, `S1: закрыто 50 из 50`) → `zabrat.sh` (`OK zabrat: 13 файлов`). Без отметки `proverka/OK` запуск отказывает. Эталон Мака — не доказательство для x86: решает шаг 4 на сервере.
