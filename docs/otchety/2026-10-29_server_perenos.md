## Шаг 1. На Маке: собрать `perenos/` (одна команда)
```
scripts/server/sobrat_perenos.sh <коммит>
```
Каталог — `perenos/` в корне (нужен пустой; другой — `PERENOS_OUT=...`). Считает эталон Мака (якорь A_fix × 6 Sk и 200 точек), ~1,5 мин на 3 процессах. Ожидается: `OK manifest: 201 файлов, 1.136 ГБ, max_data 2021-12-31, ...`, затем `etalony: ... записей 206, со status = oshibka 0`, последняя строка `OK perenos: ...; kod <12 знаков> (tar sha256 <64>); данных 201 файлов, 1,1G`. Хэш tar (`VERSIYA`) — в журнал. Если в манифесте файл с датой > 2021-12-31 или путь `test_locked` — `FAIL manifest: ...`, каталог не собирается.
Усечённые копии (`data/server_2021/`) берутся из основной копии; если их там нет — `python3 scripts/server/usech_2021.py --koren . --vyhod <куда>/data/server_2021` и `PERENOS_DANNYE_DOP=<корень копий>`.

## Шаг 4. Проверка якоря
```
./proverka_yakor.sh
```
Сравнение в два уровня (разбор: `docs/otchety/2026-10-29_kross_arh_ekviv.md`). Дискретное — строго: хэши данных, куба и дат по Sk, `kod`, `vhody`, ключи и статусы строк ledger, сделки по дням, индексы входа/выхода. Непрерывное — Шарп, доходности, ряды: якорь ≤ 1e-12 (Ж-131), точки — допуск из переменной `DOPUSK` (по умолчанию 0, побайтно; меняет только владелец: `DOPUSK=1e-12 ./proverka_yakor.sh`).
Ожидается две строки: `proverka[режим 1]: max |Δ| непрерывных: якорь ... , точки ...; дискретных расхождений 0, непрерывных вне допуска 0` (max |Δ| печатается всегда, и при OK) и `OK [режим 1]: дискретное совпало; ...; отметка .../proverka/OK`. Параметры numba (`NUMBA_NUM_THREADS=1`, `NUMBA_THREADING_LAYER=workqueue`) скрипт печатает и ставит сам, они те же, что при эталоне на Маке.
Режим numpy: `./proverka_yakor.sh --rezhim2` прогоняет оба режима (1 — numpy как есть, 2 — без AVX512-группы и SVML, `NPY_DISABLE_CPU_FEATURES` + `NPY_DISABLE_SVML=1`) и печатает оба итога; режим выбирает владелец и дальше задаёт `PERENOS_REZHIM=<1|2>` при `./zapusk_sobol.sh` (нужна отметка `proverka/OK` либо `proverka/OK_r2` того же режима). Если numpy на сервере ругается на имя в списке AVX512 — список меняется переменной `PERENOS_REZHIM2_FEATURES` (имена из `numpy.show_runtime()`).

**Что делать при FAIL.**
- `FAIL дискретное` (код 1): стоп. Счёт не запускать, ничего не менять, вывод и `proverka/verdikt_*.json` — дирижёру. Это перевернувшаяся сделка, другой ключ ledger (`vhody`) или другие данные; допуском не лечится.
- `FAIL непрерывное` (код 3): дискретное совпало, но Шарп/доходности вне допуска. Счёт не запускать; прислать дирижёру строку FAIL и max |Δ| (якорь и точки). Расширить `DOPUSK` или принять режим 2 решает владелец.
- `OK` при max |Δ| > 0 (допуск владельца): значения в допуске; max |Δ| записать в журнал.
Локально, на том же arm64, Δ = 0.0; на x86 расхождение возможно — это и проверяется.

## Шаг 5. Запуск счёта (в фоне)
```
./zapusk_sobol.sh train4
./zapusk_sobol.sh v2
./zapusk_sobol.sh status train4
```
**Процессы.** Каждая цепочка берёт `(ядра − 4) / 2`: train4 и v2 идут вместе, сумма ≤ ядра − 4 (при 132 ядрах — по 64). Перед стартом скрипт складывает процессы живых цепочек (`logs/sobol_<период>.procs`) и при сумме > ядра − 4 отвечает `FAIL: процессов уже занято другой цепочкой ...`. Одна цепочка на весь сервер — `PERENOS_CEPOCHEK=1`.
**Объём (N1).** Проходы s1 и s2 считают N1 = **262 144 индекса Соболя на стратегию** (решение дирижёра, `docs/zadaniya/2026-10-29_volna_17.md` п. 1: «200 000» → степень двойки; после выброса `canon_v5` у S1, S2, S5, S6 посчитано около 152 тыс. точек). Другое число — `PERENOS_N1=<число>`; k3 — полная решётка раздела k3, `--n1` не принимает.
Выбранный режим numpy: `PERENOS_REZHIM=2 ./zapusk_sobol.sh ...` (по умолчанию 1). Каждый запуск делает проходы `PERENOS_PROHODY` (умолчание `s1 s2 k3 spravka`) по кубу v5 подряд: `--kub v5 --period <период> --seed 1|2` или `--k3`, процессов — ядра − 4, ledger — `ledger/<период>_<s1|s2|k3>/<Sk>/`, чекпоинт каждые 5 000 точек (`checkpoint.json`), возобновление — повтор той же команды. `status` печатает по каждой стратегии `N=… чекпоинт i=…`. Остановить — `kill <pid>` из `status`. Без отметки шага 4 (того же кода, данных, эталона и режима) — `FAIL: нет отметки proverka/OK`, счёт не стартует.
**Справочная строка spravka (Ж-137 п. 6; умолчание дирижёра, `tolkovaniya.md` 29.10 19:10; лист P-4).** Четвёртый проход цепочки (умолчание `PERENOS_PROHODY` = `s1 s2 k3 spravka`) — те же точки, что s1 (seed 1, N1), но выход по close дня: `fastbt.progon_server --kub v5 --period <период> --seed 1 --n1 … --rol spravka --t-vyhod close`. Ledger 2.2 с `rol = spravka`, каталог `ledger/<период>_spravka_close/<Sk>/`; идёт после полных проходов, на всех периодах (train4, v2, wf — wf только с отметкой владельца). В N не входит: `ledger_v2.Obedinenie` пропускает `rol ∈ {kontrol, spravka}` (тест `tests/test_progon_spravka.py`). `svodka_ledger.py` показывает его отдельной строкой `spravka close <период>`. Только spravka: `PERENOS_PROHODY=spravka ./zapusk_sobol.sh train4`. Порядок для v5: полный проход (`s1 s2 k3`) → `spravka`. Для v6 (куб `PERENOS_KUB=v6`, когда `progon_server` его принимает): Моррис → заморозка → полный → `PERENOS_PROHODY=spravka`; раздел «v6» (команды Морриса и заморозки) ведёт лист М-драйвер, здесь — только строка spravka и порядок.
Ожидается: `OK zapusk train4: pid N, лог logs/sobol_train4_<время>.log`, в логе по окончании `S1: посчитано …, ошибок 0, чекпоинт …, сбой None` по каждой стратегии и `цепочка train4 завершена`.
Малый прогон (как проверялось на Маке): `PERENOS_PROHODY=s1 PERENOS_N1=64 PERENOS_STRATEGII=S1,S2 ./zapusk_sobol.sh train4` (≈ 1 мин; посчитано 35 и 38 из 64 — часть точек куба v5 выбрасывает `canon_v5`); `PERENOS_PROHODY=k3 PERENOS_STRATEGII=S3 ./zapusk_sobol.sh train4` (k3 — полная решётка, `--n1` не принимает: S3 = 560 точек, ≈ 11 мин на 4 процессах).

## Шаг 6. Забрать результаты (на Маке)

Забирает `tables/`, `logs/` и из `ledger/` — `manifest.json`, `checkpoint.json`, `SHA256SUMS*`, `daty.npy` каждой стратегии; шарды `p*/` — только у ledger 2.1 (`"v": "2.1"` в manifest). Шарды ledger 2.0 остаются на сервере. ↺ сужение Ж-131 п. 3 («обратный rsync: ledger, таблицы, логи») по решению дирижёра (`volna_17` п. 3) · откат: забрать 2.0 по запросу отдельной командой rsync (29.10). Проба без копирования: `PERENOS_DRYRUN=1 ./zabrat.sh ...`. Ожидается `OK zabrat: N файлов в ... (tables/, logs/, ledger: 2.1 — k стратегий с шардами, 2.0 — m без шардов)`. Если в забранном код или данные — `FAIL`.
Сводка (на Маке, из корня репозитория): `python3 scripts/server/svodka_ledger.py data/server_rezultaty/<ДД-ММ>/ledger/train4_s1 --top 1` — таблица по Sk; ожидается колонка `sverka` = `ok`, один `kod` и один `vhody` на каталог. ## Период wf (единый walk-forward, Ж-136 п. 5; лист P-2)
До снятия замка владельцем (`test_locked/`, `zamki.json`) всё работает как выше, на данных ≤ 2021. Для wf:

## v6: Моррис → заморозка → полный проход
Порядок (Ж-137 п. 2): сначала Моррис ~5 000 точек на Sk по кубу v6, потом `zamorozka.yaml`, потом полный проход с замороженными осями на «выкл.».
1. Моррис (оценщик `EvaluatorV6` строится один раз в родителе, fork, flock на каталог, чекпоинт; повтор той же команды с `--prodolzhit` возобновляет):
```
python3 -m fastbt.progon_morris_v6 --kub v6 --period train4 --out <каталог> --procs <ядра − 4> [--strategii S1,S2] [--r N]
```
   `r` по умолчанию = 5 000 // (k + 1), k — готовые оси куба (`canon_v6.GOTOVY`). `--r 1` — малая проверка (одна траектория). Период — `train4` (план §3.3); `v2` допустим, `wf` отказывает (даты ≥ 2020 в рядах).
2. Выход в `<каталог>/<Sk>/`: `morris_y.jsonl` (Y трёх окон ≤2016, ≤2017, ≤2018 по уникальным точкам), `morris_<Sk>.csv`, `zamorozka.yaml` (правило `morris_v6_zamorozka`: U95 < 0,05 в трёх окнах и n_akt ≥ 20; оси v5 не замораживаются; ось, все родители которой заморожены, — тоже). Печатается число ошибок точек с причинами (точка с ошибкой — Y = NaN, шаг не считается). Копии в репозиторий (`docs/tables/setka_v6/morris_<Sk>.csv`, `fastbt/designs/v6/zamorozka_<Sk>.yaml`) кладёт дирижёр после проверки, до Соболя.
3. Полный проход: точки — `fastbt.progon_morris_v6_polnyj.tochki_polnye(sid, prochitat("<каталог>/<Sk>/zamorozka.yaml"), n0, n1)`: замороженные оси вынуты из куба (размерностей Соболя меньше), в каноне их нет. ❓ Серверного Соболя по кубу v6 в базе нет (`progon_sobol.tochki` знает `progon` и `v5`): подключить `tochki_polnye` к нему — отдельный лист.
Ограничение: `IstochnikiV6` (ряды для rel_signal, К9–К24, события, внешние условия) в базе не собирается ни одним загрузчиком, поэтому оси, которым нужны эти ряды, на реальных данных дают ошибку точки (`ось … включена, а в IstochnikiV6 нет …`) и остаются «не измерено» (n_akt < 20, не заморожены). Малая проверка на Маке (1 траектория S1, train4): 20 точек, 19 с этой ошибкой.
