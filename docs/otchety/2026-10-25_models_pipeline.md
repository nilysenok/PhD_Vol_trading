## Стадии и кэш

данные → признаки → Dataset → прогнозы → HAR-J-семейство → гибрид → сводка. Ключ стадии = sha256(входы + параметры + git-версии файлов стадии;
версия = `git hash-object`, считается в процессе, сверено с git). Пересчитывается только затронутое: обучение кэшируется отдельно
(ключ = признаки шага × модель × гиперпараметры × протокол обучения × версии `train.py`/`data.py`), гибрид — по ключам своих входов.
Тёплый прогон не поднимает пул вовсе.

- **данные** (`data.py`): склейка `prepared/` как `tune_B.load` или одна матрица (`features_pit_v2.parquet` + `.config.json`); путь к матрице и колонки цели по h — параметры дизайна (`data.features`, `data.target`); `clean_features` один раз на всю матрицу (`X.npy`, mmap в воркерах).
- **признаки** (шаг × h): индексы строк train_pure / val / тест / год после теста и цель ln(rv + 1e-10) — как `tune_B.step_data`.
- **Dataset** (шаг × h × модель × max_bin × float32): `lgb.Dataset.save_binary` (train + val с reference) и `xgb.DMatrix.save_binary`. Для протокола B v2 датасеты строятся в воркере (`QuantileDMatrix` не сохраняется в файл; бины шагов ≥ 2 — от шага 1 через reference).
- **прогнозы** (`train.py`, `v2.py`): пул процессов `spawn`, num_threads = 1 на модель, очередь — длинные первыми (LightGBM раньше XGBoost, поздние шаги раньше); каждое обучение пишет val → `val/boost/`, test → `test_locked/boost/`, год после теста → `test_locked/boost_next/` (для Д8.4).
- **HAR-J-семейство** (`hybrid.py`): `gibrid_har.har_forecasts` (строки (а)/(б)) и `gibrid_har_spec.run` (строка (в)) без правок.
- **гибрид**: `gibrid_v17.run_h` по одному h как есть (после слияния базы — пространство Д8: схемы, поправки, усадка, смешивание rv/log, V0, c1–c4, правило); прогнозы конвейера подаются как П1 (вариант single); h запускается, как только готовы все обучения h.
- **сводка**: одна таблица по h и наборам (разработочный — шаги 2–6, val 2017–2021, метрика вне выборки как в `gibrid_v17 --dev-eval oos`; подтверждающий 2022–2024 — только `--confirm` по команде дирижёра). Для ворот — `--all-steps`: шаги 7–9 считаются, их метрики не показываются.

Тест закрыт: метрики по `test_locked/` — только `--scope test`, который падает без `docs/otchety/FINAL_DESIGN.md` (проверено).

Находки по воротам:
1. **CSV обрезает гиперпараметры.** `B_grid_100.csv` / `B_selected.csv` записаны pandas с 15–16 знаками; lightgbm считает в double, и дизайн из CSV даёт другие прогнозы (до 1e-5 по RV, lgbm h = 1 шаг 6). Конвейер берёт точку по номеру из сетки `make_grid` скрипта B (исполняется через ast), CSV конвейера пишутся с `%.17g`.
2. **B: в одной ячейке из 54 QLIKE в `B_trials.csv` ≠ рефит** (lgbm h = 5 шаг 2: 0,2882 против 0,2953, best_iteration 62 против 65). `B_selected.qlike_val` взят из перебора, прогнозы `B_*.parquet` — из рефита; конвейер воспроизводит рефит. Повторное использование `lgb.Dataset` между точками причиной не является (проверено: 6 «предыдущих» точек, расхождение 0,0) — для агента B.
3. xgboost не открывает `DMatrix` из файла по пути с кириллицей («Старое») — загрузка по относительному имени из каталога датасета.

Вывод — одна таблица и строка «время, лог»; логи — `data/run/*.log`, при ошибке в консоль — только хвост лога.

- **Переподбор**: optuna TPE, 30 испытаний, seed 42, пространство = `SPACE` из `tune_B.py`, критерий — val-QLIKE шага; один study (модель × h × шаг) = одна задача воркера (один Dataset на воркер), испытания подряд — детерминированно; отсечение: на итерации 100 val-QLIKE хуже лучшего завершённого испытания на 20% → `PRUNED` (прогнозы снятых тоже сохраняются, флаг `pruned`). Объявляется как процедура поиска уровня 2 и финальной комбинации; B (ЛГК 100) не меняется. Выход — `data/models_cache/tune/selected_*.csv` (формат `B_selected`, → `mkdesign`).

- **Ускорения 25.10, 18:25**: `force_col_wise`, вход float32 — в `DEFAULT_TRAIN` (в протоколе B выключены: меняют бины lightgbm и ломают ворота), очередь длинных первыми, группировка испытаний study в одном воркере, отсечение, 10 воркеров.

## Рычаги на точке B v2 (подготовлены, не считались — по команде)

`models/designs/{v9,d812,d84,d86}.yaml` (h = 5, 22; точки `Bv2_selected_h*.csv`, протокол v2), база — `bv2_base.yaml`; сравнение — `models compare` (остаётся при улучшении QLIKE гибрида по правилу на разработочном наборе ≥ 1% или снятии нарушения критериев). Все четыре прошли `--smoke`.
- V9 (`harj_residual`): цель ln RV − ln F_HARJ_corr, σ = F_HARJ_corr · exp(прогноз остатка); F_corr = exp(ŷ + s²/2), HAR-J — `etap2_okno.fit_predict` на train_pure шага, s² — остатки обучающего окна.
- Д8.12 (`harj_feature`): ln F_HARJ_corr как признак.
- Д8.4 (`avg_prev_step`): val шага t = среднее(модель t, модель t−1 на своём тест-году), test — модель t−1 на году t+1; обучения те же, что у базы (из кэша).
- Д8.6 (`h1_feature`): ln-прогноз модели h = 1 (точка B v2) как признак на h = 5/22; на строках обучения он внутривыборочный — оговорка, проверяется только на валидации.

## Отступления

- ↺ Тестовые прогнозы бустинга читаются стадией гибрида для смешивания (не метрики) и воротами для тождества файлов (не метрики).
- ↺ Замер переподбора делался с `--confirm` (все 9 шагов): в выводе показан val-QLIKE 2022–2024 подобранных optuna точек h = 22 (lgbm 1,095, xgb 1,044). Решений по нему не принималось; в счётчик просмотров подтверждающего набора. Так же при воротах гибрида после слияния видны val 2022–2024 одиночных HAR-J/XGB/LGB П1 (были известны раньше). Впредь — `--all-steps` для ворот, `--confirm` только по команде.
- ↺ Протокол B v2 в конвейере: ES по l2 (как в коде tune_Bv2.py), а не по QLIKE, как в описании протокола — воспроизведён код.
