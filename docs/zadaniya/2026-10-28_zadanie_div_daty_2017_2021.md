# Задание kodir — даты отсечки 2017–2021 по правилу T+2 баров (PR данных, `pravki.md` п. 12)

## Причина
В #394 цены 2017–2019 показали ошибку в таблице `docs/issledovaniya/2026-10-27_dividendy_2017_2021.csv`:
- `last_cum_date` расходится с правилом «T+2 по календарю баров» в 6 строках 2017–2019;
- ошибка доказана ценами у MOEX 2019-05-14 и TATN 2019-01-09, вероятна у PHOR 2018-03-12 и NVTK 2018-05-03;
- правило T+2 по барам попадает в день гэпа в 55 из 55 строк с D > 2 % цены, таблица — в 53 из 55.

Разбор — в теле PR #394 и в `docs/otbor/REESTR_dannyh.md`.

## Цель
1. В `fastbt/dividendy.py` `last_cum_date` считать **для всех лет** тем же правилом T+2 по календарю баров, что уже работает для 2015–2016 (#394, слит).
   - Файл исследования не править. Колонка таблицы `last_cum_date` больше не используется для PnL, только для сверки.
   - Для 2020–2021 правило применяется **без проверки ценами** — это годы validation.
2. **Было / стало без метрик:** таблица «тикер, реестр, `last_cum_date` по таблице → по правилу», только строки, где они различаются, по всем годам 2017–2021.
3. Последствия:
   - `digest()` меняется;
   - кэши s9 и etap1 инвалидируются;
   - **эталоны `final3` на этом коде разойдутся.** Эталоны **не пересчитывать**: они под замком владельца, решение ждёт ответа (вопрос дирижёра 10:36).
   - В отчёте назови, какие тесты покраснеют: `test_s9_scope::test_dev_reproduces_final3_tables` и т. п. Запусти их с `--tb=no`, значения не выводи.
