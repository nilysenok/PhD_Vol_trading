# Канон для работы с ИИ-агентами: универсальные дополнения (v23)

Документ-источник для запроса в Claude Code. Не привязан к проекту: подставляются только пути и команды. Основан на открытых практиках (unlazy-скиллы, хуки Claude Code, гайды по оркестрации, протоколы аудита бэктестов) и на ошибках, пойманных в реальной работе 26–27.10.

---

## 0. Главный принцип: три слоя принуждения

Правило в тексте канона — просьба. Агент её обычно выполняет, но под нагрузкой контекста забывает. Поэтому каждое правило канона относится к одному из трёх слоёв, и слой выбирается по цене нарушения:

| Слой | Что это | Когда |
|---|---|---|
| Текст (CLAUDE.md, rules) | рекомендация | стиль, порядок работ, форма отчёта |
| Хук (`.claude/hooks`) | код, который блокирует или проверяет действие | всё, что нельзя нарушать: чтение закрытых данных, правка замороженных файлов, остановка без тестов |
| Права (`settings.json` permissions) | инструмент недоступен вообще | команды и пути, которые агенту не нужны никогда |

Правило канона: **если нарушение правила испортило бы результат (утечка, подмена, потеря), оно обязано быть хуком или правом, а не абзацем.** При каждой пойманной ошибке первый вопрос — «какой хук её бы не пропустил».

Минимальный набор хуков:
- `PreToolUse` (Read/Bash/Grep): запрет чтения закрытых путей (тестовые данные, замороженные отчёты) всем, кроме скрипта открытия; запрет правки файлов под замком; запрет `rm -rf`, force-push, правки конфигов линтера/тестов в обход.
- `PostToolUse` (Write/Edit): линтер + быстрые тесты затронутого модуля; запись в аудит-лог `audit.jsonl` (кто, что, когда, хэш).
- `Stop`: полный тестовый прогон модулей, затронутых в сессии; при падении — код 2 (агент продолжает чинить, а не докладывает «готово»); проверка, что нет незакрытых гейтов в `GATES.md`.
- `PreCompact`: автоматическая запись файла передачи (задача, решения, блокеры, незакрытые гейты) до сжатия контекста.
- `SessionStart`: загрузка последнего файла передачи и журнала решений.

## 3. Данные и информационное множество

1. **Проверка сдвига обязательна для каждого входного ряда** до первого использования и после каждой регенерации: корреляция с целевой величиной при сдвигах −2…+1, максимум должен быть на последнем известном дне; для оконных рядов — по приращениям; для рядов с плоским профилем — вторая проверка через связанную величину. Результат — первая строка журнала шага. Ряд без проверки в расчёт не входит (хук на загрузку данных проверяет наличие отметки).
2. **Лаг исполнения по умолчанию.** Решение на закрытии дня d исполняется не раньше d+1 (или по закрытию d, если это явно объявлено и обосновано). Тест «исполнение в том же баре, что и сигнал» обязан падать.
3. **Point-in-time.** Любой ряд хранится с датой, когда значение стало известно (решение ЦБ ≠ вступление в силу; отчётность ≠ дата периода; пересмотры данных — отдельными версиями). Календарь торгов, остановки, корпоративные события — отдельные файлы с хэшами.
4. **Константа в данных — ошибка, пока не доказано обратное.** Любая подстановка (ffill, bfill, среднее, ноль) на отрезке длиннее одного наблюдения требует отметки в журнале и теста, что она не влияет на результат.
5. **Ключ кэша = хэш всех входов и кода.** Ряды, параметры, версия кода, конфиг. Проверка: подмена любого входа при том же ключе обязана давать промах кэша (тест с мутацией).
6. **Эталонные таблицы** (golden) для каждого этапа пайплайна; после исправления ошибки старые — в архив с хэшами и причиной, новые генерируются с исправленного кода; сверка побайтно или с допуском, объявленным заранее.
7. **Одно определение на метрику** на весь проект (например, ddof, годовая шкала, база избыточной доходности). Два определения в одной таблице запрещены; смена определения — PR с пересчётом всех таблиц и строкой «что изменилось».

## 4. Отбор, статистика и предрегистрация

1. **Сетка объявляется до счёта** и коммитится; число точек N фиксируется и идёт в поправки (Холм, DSR). Расширение сетки после просмотра — допустимо на разработочном наборе, но записывается как расширение с датой и причиной, N обновляется.
2. **Контроли без модели обязательны** для любого утверждения о ценности модели: (а) тот же дизайн с «ничего не знающим» входом (константа/безусловное среднее); (б) тот же дизайн с перемешанным или циклически сдвинутым входом (сохраняет распределение и автокорреляцию, разрушает привязку ко времени), p по перестановкам; (в) база без того компонента, ценность которого утверждается.
3. **Запрет дизайнов с внутренним выбором на единицу наблюдения** (выбор варианта на каждый объект/год по валидации) в кандидаты на тест: они неустойчивы к микросдвигам входа. Только фиксированные точки + таблица плато соседей.
4. **Реестр отбора**: все кандидаты, все метрики, все флаги условий — в одной таблице, которая не редактируется, только дополняется. Ничто не удаляется «как неудачное».
5. **Пороги выхода на тест** фиксируются после базы и до перебора вариантов; после просмотра вариантов не двигаются. Deflated Sharpe (или аналог для данной метрики) с фактическим N — обязательный порог.
6. **Одно открытие теста** на раунд; скрипт открытия: отказывает без строки «да» владельца с датой, при несовпадении хэшей кода и входов, при наличии незакрытых гейтов; ставит замок до чтения данных; пишет всё за один прогон. Всё, что считалось на тестовых данных до открытия (ошибочно или случайно), помечается и выносится в отчёт как просмотр.
7. **Изменение эталона или гипотезы после просмотра результата** — только с явной записью «отступление от предрегистрации», причиной и обеими версиями результата.
8. **Метрики — набор, а не одно число**: для стратегий — избыточный Шарп, модифицированный Шарп (Cornish–Fisher), Сортино, Кальмар, MDD, PSR/DSR, оборот, доля исполнений; для прогнозов — основная функция потерь + DM несколькими способами + MCS. Самое выгодное число не выбирается задним числом: какая метрика основная — объявлено до теста.

## 5. Проверка кода и результатов

1. **Тест с подложенной ошибкой** (мутация) обязателен для каждого PR, меняющего пайплайн: тест должен падать на мутации и проходить на правке. Список обязательных мутаций по теме хранится в `rules/mutations.md` (сдвиг входа, касание уровня, порядок событий в баре, комиссия на границе, ключ кэша, N в поправке).
2. **Разделение ролей** (автор / тестировщик / ревьюер) и **перепроверка родителем** — см. §2.
3. **Быстрый и медленный слой**: любая оптимизация скорости сверяется с эталонным медленным путём побайтно (или с объявленным допуском) на фиксированном наборе точек; сверка — в CI.
4. **Статус результата в каждой таблице**: «до аудита / после аудита / разработка / тест», версия кода, хэш входов — в шапке файла, не в сопроводительном письме.
5. **Проверка по известному ответу**: синтетические данные, где правильный результат известен, для каждого модуля (исполнение сделок, метрики, бутстрап, DM).

---

## 6. Связь с владельцем

1. Блоки владельца нумеруются (дата-время или сквозной номер); главная сессия отвечает квитанцией «принят блок N» до исполнения; журнал решений — файл только для добавления; блок без квитанции считается не дошедшим.
2. Решения владельца пишутся дословно, толкование — отдельной строкой; при расхождении приоритет у дословного.
3. Вопрос владельцу — только с умолчанием и сроком («если нет ответа до T, делаю X»); вопросов в одном сообщении — не больше трёх, с номерами.
4. Отчёт владельцу: результат первой строкой; что не сделано; что отступило; что требует решения; без пересказа задания.
5. Время — только по часам машины, где идёт работа.
6. Чувствительные данные (личные, финансовые, служебные) — в отдельном файле вне репозитория; агенты получают их только через переменные окружения или по явной команде.

## 7. Структура канона и файлы

```
CLAUDE.md                 ≤150 строк: роли, абсолютные запреты, порядок работ, указатели
.claude/rules/
  polnota.md              §1
  orkestratsiya.md        §2
  dannye.md               §3
  otbor_statistika.md     §4
  proverka.md             §5
  svyaz.md                §6
  mutations.md            обязательные мутации по темам
.claude/hooks/            §0
.claude/settings.json     permissions: deny-списки путей и команд
templates/
  GATES.md, zadanie_agentu.md, otchet_agenta.md, handoff.md, FINAL_DESIGN.md
docs/resheniya/           журнал решений владельца (append-only, нумерация)
docs/otchety/             отчёты с хэшами
```

Задание агенту ссылается на конкретные файлы `rules/`, а не на «канон целиком».

## 8. Как измерять, что канон работает

Раз в неделю главная сессия считает и записывает:
- число блоков владельца без квитанции (цель 0);
- число ошибок класса «сдвиг / утечка / кэш», найденных после слияния (цель 0; найденные до слияния — норма);
- доля PR с тестом-мутацией (цель 100 % для пайплайна);
- среднее число токенов агента до передачи (цель ≤ 300k);
- число молчаливых отступлений, обнаруженных ревьюером (цель 0);
- число открытий теста за раунд (цель 1).

Если метрика ухудшилась — правка канона в тот же день, с указанием, какой хук или правило добавлены.
